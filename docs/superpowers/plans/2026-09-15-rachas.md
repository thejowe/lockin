# Rachas de pareja — plan de implementación

**Goal:** Que cada pareja (match) vea cuántas sesiones Lock-In compartidas lleva
seguidas —con un hueco de menos de 7 días entre una y la siguiente— en la
tarjeta de sesión del chat y en su fila de Matches, sin que la racha lea ni
revele la valoración de nadie.

**Architecture:** Nada se guarda. Una función pura `pairStreak` en
`src/data/streaks.ts` y su espejo en SQL, el RPC `match_streaks()`
`SECURITY DEFINER` que reutiliza `session_both_attended`. Un método nuevo,
`listStreaks()`, en el `LockInSessionRepository` que ya existe, cumplido por el
mock y por Supabase bajo la misma suite de contrato. La UI lo lee en la tarjeta
(vía `useActiveSession`) y en la lista de Matches (vía `useMatchStreaks`).

**Tech Stack:** Expo SDK 57, React Native 0.86, expo-router 57.0.21, TypeScript
estricto, Jest (`jest-expo`) + React Native Testing Library 14 (`render`,
`fireEvent` y `renderHook` asíncronos), Supabase (Postgres 17, PostgREST),
PGlite 0.3.14 (`npm run test:schema`), Maestro para E2E Android.

**Spec:** `docs/superpowers/specs/2026-09-15-rachas-design.md`

## Global Constraints

- Cuenta una sesión `aceptada` con asistencia de **las dos** personas
  (`joinedAt < endsAt`). Suma al entrar la segunda, sin esperar al final.
- Seguidas si `siguiente.startsAt − anterior.endsAt < 7 días` (estricto). Viva
  mientras `now < última.endsAt + 7 días`. `STREAK_GAP_DAYS = 7`.
- Plantones, canceladas, rechazadas y caducadas **ni suman ni rompen**.
- **Nunca se lee `session_ratings`**, ni en SQL, ni en el mock, ni en la UI. Es
  lo que impide que la racha filtre la valoración privada.
- `listStreaks()` devuelve solo matches del actor con racha viva (`count ≥ 1`).
  La UI pinta desde 2 (`STREAK_MIN_VISIBLE = 2`).
- Sin errores de dominio nuevos. `session-errors.ts` no cambia.
- Sin tablas, enums, políticas ni publicación Realtime nuevas.
- Las pantallas importan datos solo desde `@/data`, nunca desde `@/data/mock`
  ni `@/data/supabase`. `src/features/chat/` **no** importa de
  `@/features/session`: `MatchRow` recibe un número.
- **Cruces de alcance, y solo estos:** `src/app/(tabs)/matches.tsx`,
  `test/app/matches.test.tsx`, `src/features/chat/match-row.tsx`,
  `src/features/chat/match-row.test.tsx` (bloque `chat`) y `test/routes.tsx`
  (bloque `calidad`). Cualquier otro archivo fuera de `sesiones`: **para y
  dilo**.
- `src/app/session/[sessionId].tsx` **no se toca**.
- Worktree compartido: **nunca `git add .`**; cada commit añade rutas explícitas.
- En RNTL 14 `render`, `fireEvent` y `renderHook` devuelven promesas: `await`
  siempre.
- Textos de UI en español; comentarios de código en español.
- `.sql` en LF (`.gitattributes` ya lo fija).
- El suelo de cobertura de `jest.config.js` (89.82/82.56/91.49/91.38) **no baja**.
- No se lanza a la vez que `sesiones` ni que `valoracion`: mismo dueño de
  archivos.

## Qué se puede probar contra Supabase real, y qué no

Al revés que la valoración, **una racha de 1 sí se puede fabricar contra
Supabase real**: `propose_session` exige `starts_at ≥ now() + 5 min`, pero la
ventana de entrada abre 5 minutos antes, así que una sesión que empieza en 5 min
y unos segundos se acepta y se entra enseguida (es lo que ya hacen los casos con
`fixture.elapse(3_000)` de `repositories.contract.ts`). Esos casos van con `it`.

**Una racha de 2 o más no**: solo cabe una sesión viva por match, y la primera
dura 30 minutos de reloj. Esos casos van con `itWithTimeTravel` (saltados contra
Supabase) y **el SQL de las cadenas se cubre en PGlite** (Tarea 3), que inserta
filas con `starts_at` en el pasado. No te saltes la Tarea 3 pensando que el
contrato cubrirá el SQL.

- [ ] **Step 2: Regla pura**

`src/data/streaks.ts`:

```ts
/**
 * Regla de las rachas de pareja.
 *
 * Una sola fuente para el mock y la UI. El SQL de
 * `supabase/migrations/20260915000200_match_streaks.sql` la repite en
 * `match_streaks()`: si cambia una, cambian las dos.
 */

import { sessionEndsAtMs, type SessionTiming } from './sessions';

export const STREAK_GAP_DAYS = 7;

const GAP_MS = STREAK_GAP_DAYS * 24 * 60 * 60_000;

/**
 * Longitud de la última cadena de sesiones seguidas, o `null` si no hay o ya
 * caducó. `shared` son las sesiones que ya cuentan (aceptadas y con las dos
 * personas dentro): filtrarlas es cosa de cada backend. Da igual el orden.
 */
export function pairStreak(
  shared: readonly SessionTiming[],
  nowMs: number
): { count: number; aliveUntilMs: number } | null {
  const ordered = [...shared].sort((a, b) => Date.parse(a.startsAt) - Date.parse(b.startsAt));
  let count = 0;
  let lastEndsAt = -Infinity;
  for (const session of ordered) {
    const startsAt = Date.parse(session.startsAt);
    count = startsAt - lastEndsAt < GAP_MS ? count + 1 : 1;
    lastEndsAt = sessionEndsAtMs(session.startsAt, session.blocks);
  }
  if (count === 0 || nowMs >= lastEndsAt + GAP_MS) return null;
  return { count, aliveUntilMs: lastEndsAt + GAP_MS };
}
```

```sql
-- LockIn — rachas de pareja (Fase 2).
--
-- Diseño: docs/superpowers/specs/2026-09-15-rachas-design.md.
-- Espejo de `pairStreak` en `src/data/streaks.ts`: si cambia la regla aquí,
-- cambia allí, y al revés.
--
-- Nada se guarda: la racha se calcula al leer. La caducidad depende de now() y
-- ningún trigger la dispararía, así que un número guardado habría que
-- recompararlo igual.
--
-- NO lee `session_ratings`, y no es un descuido: la valoración es privada de
-- quien la escribe, y una racha que dependiera de ella la delataría a la otra
-- persona del match al subir o no subir.

create or replace function public.match_streaks()
returns table (match_id uuid, streak_count integer, alive_until timestamptz)
language sql
stable
security definer
set search_path = ''
as $fn$
  with shared as (
    select s.match_id,
           s.starts_at,
           public.session_ends_at(s.starts_at, s.blocks) as ends_at
    from public.lockin_sessions s
    join public.matches m on m.id = s.match_id
    where (select auth.uid()) in (m.profile_a, m.profile_b)
      and s.status = 'aceptada'
      and public.session_both_attended(s.id)
  ),
  marked as (
    select match_id, ends_at,
           case
             when starts_at - lag(ends_at) over w < interval '7 days' then 0
             else 1
           end as starts_chain
    from shared
    window w as (partition by match_id order by starts_at)
  ),
  chained as (
    select match_id, ends_at,
           sum(starts_chain) over (partition by match_id order by ends_at) as chain
    from marked
  ),
  last_chain as (
    select distinct on (match_id)
           match_id, count(*) as streak_count, max(ends_at) as last_ends_at
    from chained
    group by match_id, chain
    order by match_id, chain desc
  )
  select match_id,
         streak_count::integer,
         last_ends_at + interval '7 days'
  from last_chain
  where now() < last_ends_at + interval '7 days';
$fn$;

revoke execute on function public.match_streaks() from public, anon;
grant execute on function public.match_streaks() to authenticated;
```

Donde es fácil equivocarse:

- `lag(...)` es `null` en la primera sesión de cada match; `null < interval` da
  `null` y el `case` cae en `else 1`. Es lo que queremos: la primera empieza
  cadena. No lo "arregles" con `coalesce` a un valor que la una a nada.
- `< interval '7 days'` estricto, igual que `pairStreak`. Un `<=` hace que el
  hueco de 7 días exactos no rompa, y el test de la Tarea 1 y el de PGlite lo
  pillan.
- Sin `alter publication`. Sin tablas ni políticas.
- Si `drift-check.mjs` no detecta la función, revisa que la cabecera sea
  `create or replace function public.match_streaks(` en una línea; el arreglo
  es la migración, no el script.

```ts
import { formatStartsIn } from './format';

import type { MatchStreak } from '@/data';

/** "Racha 1" no dice nada que la tarjeta no diga ya. */
export const STREAK_MIN_VISIBLE = 2;

/** El número a pintar, o `null`. Caduca en pantalla sin volver a pedir datos. */
export function visibleStreak(streak: MatchStreak | null | undefined, nowMs: number): number | null {
  if (!streak || streak.count < STREAK_MIN_VISIBLE) return null;
  return nowMs < Date.parse(streak.aliveUntil) ? streak.count : null;
}

/** Etiqueta corta de la fila de Matches. */
export const streakTag = (count: number) => `· Racha ${count}`;

/** Línea de la tarjeta, y también del `accessibilityLabel` de la fila. */
export const streakLine = (count: number) => `Racha de ${count} sesiones seguidas`;

/**
 * "Sin sesión, se rompe en 6 días". Relativo y no con día de la semana: una
 * racha que acaba de sumar caduca el mismo día de la semana siguiente, y
 * `formatSessionWhen` lo pintaría como si fuera hoy.
 */
export const streakDeadline = (streak: MatchStreak, nowMs: number) =>
  `Sin sesión, se rompe ${formatStartsIn(Date.parse(streak.aliveUntil) - nowMs)}`;
```
